# next-dj examples

Each folder below is a self-contained Django project that runs on SQLite and Django's in-process `LocMemCache`. No Docker and no external services are required. Only [`kanban/`](kanban/) and [`live-polls/`](live-polls/) carry a Vite toolchain and need Node, every other example loads Tailwind from the Play CDN with no build step. Every app follows the canonical next.dj layout described under the conventions below. Each example also registers a project-level page root through `PAGE_BACKENDS["DIRS"]` under a name of its own, and that root owns the shared HTML envelope sitting outside the per-app page tree.

## Shared UI kit

- [`_shared/`](_shared/): shadcn-inspired component palette every example consumes through `COMPONENT_BACKENDS["DIRS"]`. Tokens (`hsl(var(--background))`, `hsl(var(--primary))`, …) live in [`_shared/static/shared/css/tokens.css`](_shared/static/shared/css/tokens.css). Components (button, card, badge, input, alert, table primitives, nav_link, page_header, app_shell, dialog, dropdown, …) live in [`_shared/_components/`](_shared/_components/) and render through the same `{% component "name" %}` tag examples already use. See [`_shared/README.md`](_shared/README.md) for the full inventory and wiring contract.

## Starter scaffold

- [`_template/`](_template/): the skeleton every example is copied from, Django's own `startproject` and `startapp` output with the canonical next.dj files, plus the shared UI kit and the test scaffold. It runs and its tests pass, but demonstrates nothing beyond the starter. [`_template/README.md`](_template/README.md) names the commands it starts from and carries the rename checklist, because each rename touches more than one file.

## Running any example

```bash
cd examples/<name>
uv run python manage.py migrate
uv run python manage.py seed_demo     # only where the example ships a demo dataset
uv run python manage.py runserver
uv run pytest
```

Tailwind is loaded via the Play CDN (`https://cdn.tailwindcss.com`) through the shared `page_head` component that every root layout calls. The same component renders the `<title>` and the rest of the head tags through `{% metadata %}`. Every example names itself under `NEXT_FRAMEWORK["SITE"]["NAME"]`, declares the viewport and its title template under `NEXT_FRAMEWORK["METADATA"]["DEFAULTS"]`, and declares its tab icon there under `icons`, an `icon.svg` shipped as an app static file. A page that wants a different tab title says so in its own `page.py`. `uv run python manage.py check --deploy --tag seo` passes clean in every example. The two Vite examples add an `npm install` plus a dev server or a build on top, documented in their own READMEs.

## Conventions every example follows

- One canonical app layout. The page tree lives in `<app>/pages/` and its components in `_components/` folders inside it, with `PAGES_DIR = "pages"` and `COMPONENTS_DIR = "_components"` spelled out in every `NEXT_FRAMEWORK`. [`admin`](admin/) keeps its components at the app root instead, in `shadcn_admin/_components/` listed in `COMPONENT_BACKENDS["DIRS"]`. DI providers, markers and named dependencies live in `deps.py`, object-permission predicates in `permissions.py`, forms and actions no single page owns in `forms.py`, signal declarations and their receivers in `signals.py`, and the framework imports all four from every installed app at startup, so no `AppConfig.ready()` has to. A `backends.py` is reserved for subclasses of the framework's backends, and domain reads sit where Django puts them, so [`search-catalog`](search-catalog/) filters through `QuerySet` methods on its models. A helper sits beside the code it serves rather than in a module of its own: the retention acknowledgement every wizard step of [`audit-forms`](audit-forms/) inherits lives in `access/forms.py`, and `get_active_tenant`, the Python reader of `request.tenant` in [`multi-tenant`](multi-tenant/), lives in `notes/middleware.py` beside the middleware that sets it.
- One project-level page root listed in `PAGE_BACKENDS["DIRS"]` (e.g. `host/`, `frame/`, `shell/`, `studio/`). The file router walks it alongside the per-app `pages/` trees, and its `layout.djx` becomes the outermost wrapper around every page. The [`markdown-blog`](markdown-blog/) example also keeps project-shared components inside this root, a `site/_components/site_footer` registered through `COMPONENT_BACKENDS["DIRS"]`, and [`multi-tenant`](multi-tenant/) registers a sibling `root_blocks/` the same way for its `header` and `footer`.
- The directories of a page tree spell its URLs, and every app tree joins the one `include("next.urls")`. [`_template`](_template/) serves `/myapp/` from `myapp/pages/myapp/`, and [`admin`](admin/) serves the activity feed from `admin_audit/pages/activity/` and the book outline and manuscript from `library/pages/library/book/[int:book]/` beside the generic pages of `shadcn_admin/pages/`. `manage.py routes` prints every URL with its name, file and access rule.
- Access is declared on the page tree. A `proxy.py` holds the access of its directory and every page below it, `proxy.login_required()`, `proxy.permission_required(perm, obj=DObject[Model])` and `proxy.public()`, and nothing else, since data and context stay in `page.py`. A `public()` deeper in the tree lifts what a `proxy.py` above requires, which is how the sign-in pages of [`admin`](admin/) stay open under its closed tree. The examples without accounts declare `page.public()` on every page whose actions anyone may post, which states that those actions are open on purpose, and `manage.py permissions` lists the rule of every page and action. `manage.py check` reports an unguarded action as `next.W129` only once a project declares access, so a project with no `proxy.py`, no page declaration and no `add_perm` hears nothing.
- `STATIC_VERSION` names the deploy stamp. Every asset URL carries it as a `v` parameter and every partial response carries it as the asset version, so shipping new assets asks open clients to reload instead of patching against stale JavaScript. The derived default reads `STATIC_VERSION` first and falls back to the hash of a staticfiles manifest, so one release tag serves both and nothing names a version twice. [`observability`](observability/) sets no tag at all, because its opt-in `ManifestStaticFilesStorage` profile is what the fallback reads. [`kanban`](kanban/) and [`live-polls`](live-polls/) let Vite hash their filenames, so they leave asset URLs untouched and pin the partial `VERSION` by itself through `next.conf.extend_default_backend`.
- Co-located CSS/JS next to the `page.py`, `component.py`, or `layout.djx` they belong to. The `{% collect_styles %}` / `{% collect_scripts %}` tags place them in the rendered HTML, with deduplication.
- Demo data lives in an app-level `demo.py` behind a `seed_demo` management command, never in a `RunPython` migration. Migrations stay schema-only, so a fresh test database starts empty and a test asks for the dataset through the example's `demo_data` fixture. Six examples ship one: [`admin`](admin/), [`feature-flags`](feature-flags/), [`kanban`](kanban/), [`live-polls`](live-polls/), [`multi-tenant`](multi-tenant/), and [`search-catalog`](search-catalog/).
- E2E tests driven by `next.testing`. Every example opts into the framework's pytest plugin from its own `pytest.ini` (`addopts = ... -p next.testing.plugin`) rather than copying a conftest: `next_pages` names the page directories imported once per session, `next_clear_cache` resets the `LocMemCache` before each test, and the `next_client` fixture is the client that speaks the partial protocol. See [`_template/pytest.ini`](_template/pytest.ini).
- Forms answer a successful submit in one of two ways. A full-cycle form redirects, either declaratively through `Meta.success_url` (plus an optional `Meta.success_message` flash, see [`shortener`](shortener/)) or by returning `HttpResponseRedirect` from `on_valid` when the target depends on the submission. A form that patches the page instead returns a `Patches(request)` envelope, which falls back to a redirect on its own when no runtime is present, so the no-JavaScript path stays intact either way. The [`admin`](admin/) example shows the access side of the same surface: declarative `login_required=True` guards on every mutating action.
- A `sitemap.py` or a robots source at the top of a page root switches `/sitemap.xml` and `/robots.txt` on, both served through `include("next.urls")` with no URL of their own, or through `include("next.seo.urls")` at the host root when `next.urls` sits under a prefix or inside `i18n_patterns`. Static routes are listed on their own and dynamic ones through `@sitemap.items`, and robots comes from a `robots.py` declaring a list of `RobotsRule` groups with the `Sitemap:` line appended by the framework ([`markdown-blog`](markdown-blog/), [`wiki`](wiki/)), or from a static `robots.txt` served as written ([`shortener`](shortener/)). The integration tests read heads and sitemaps back through `next.testing.assert_metadata` and `parse_sitemap`, and robots as plain text. Every example that publishes one sets `NEXT_FRAMEWORK["SITE"]["URL"]`, so the documents and every head URL are absolute on the published origin rather than on the request host, and pins `SITE["INDEXABLE"]` to `True`, since the default `"auto"` follows `DEBUG` and would render the dev server `noindex`. [`admin`](admin/) ships neither document, because a private site has nothing to list.
- Partial rendering runs through most of the catalog rather than sitting in one example. `{% zone %}` marks the region a patch addresses and `Patches(request)` builds the envelope that fills it: a prepend into a list in [`shortener`](shortener/), a modal wizard in [`audit-forms`](audit-forms/), a polling zone plus a project-defined patch verb in [`observability`](observability/), auto-submit filters and infinite scroll in [`search-catalog`](search-catalog/), an SSE fan-out in [`live-polls`](live-polls/), and keyed inline row forms in [`admin`](admin/).
